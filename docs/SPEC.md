# DNACode — 极简代码编辑器与 AI Git 提交工具

你是一名资深 Rust 桌面应用工程师、Vue/TypeScript 工程师和开源项目维护者。

请在当前工作目录中直接开发一个名为 **DNACode** 的轻量级桌面代码编辑器。目标是交付可以实际使用、可以构建安装包、可以发布到 GitHub 的完整开源项目。

**不要只输出计划、架构图、设计文档或代码示例。必须实际创建或修改代码、安装必要依赖、运行测试、修复问题、执行生产构建，并在当前环境允许的情况下生成实际安装包。**

遇到非关键设计决策时，直接采用合理默认值继续开发，不要频繁询问我。遇到环境依赖缺失时，尽可能完成其他工作，并明确记录真实阻塞原因。

# 一、产品定位

产品名称：DNACode。

产品副标题：Minimal Code Editor。

产品口号：Less IDE. More Flow.

DNACode 是一个专注于代码查看、基础编辑、Git 变更审查、AI 修改总结以及提交推送的极简桌面工具。

它不是 VS Code 的全功能替代品，而是刻意删减功能，只保留开发者日常使用频率最高的核心操作。

核心体验：

打开项目 → 左侧查看和编辑代码 → 右侧检查 Git 变更 → AI 总结本次修改 → 检查提交信息 → 点击 Commit → 点击 Push。

整个过程始终在同一个窗口内完成。

## 产品最重要的目标

1. 冷启动快，打开项目快。
2. 界面操作流畅，代码滚动和切换文件不卡顿。
3. 尽量减少内存占用与无意义的后台任务。
4. 界面极简，打开后无需学习即可使用。
5. Git 操作可靠，所有状态以真实仓库数据为准。
6. AI 是可选的辅助能力，不影响普通编辑和 Git 操作。
7. 代码结构清晰，适合长期维护和开源协作。

**不要为了增加功能而牺牲简洁性。**

# 二、技术栈必须固定

采用以下组合，不要在开发过程中反复更换架构：

- 桌面框架：Tauri 2。
- 后端：Rust。
- 前端：Vue 3 + TypeScript。
- 开发与生产构建：Vite。
- 包管理器：pnpm。
- 代码编辑组件：CodeMirror 6。
- Git 操作：调用系统安装的 Git CLI。
- 样式：原生 CSS 与 CSS Variables。
- 图标：轻量图标库或少量 SVG。
- AI：可配置的 OpenAI 兼容 API。
- 测试：Rust 测试、前端必要的单元测试、类型检查和生产构建。
- 发布：GitHub Actions。

明确禁止：

- Electron。
- Monaco Editor。
- 完整 IDE 框架。
- Element Plus、Ant Design Vue 等大型组件库。
- 不必要的全局状态管理框架。
- 常驻后台服务。
- 必须登录才能使用的账号系统。
- 自建 AI 转发服务器。
- 没有实际用途的复杂抽象层。
- 为了追求架构形式而过度拆分模块。

Rust 主要负责文件系统、Git、后台耗时任务、配置和安全相关操作。

Vue + TypeScript 主要负责界面、编辑器组件、状态展示和用户交互。

不要因为使用 Rust 就把所有简单界面逻辑都写到 Rust 中。也不要因为使用 Vue 就将文件系统和 Git 命令全部暴露给前端。

主窗口必须是固定的三栏结构：

1. 左侧：项目文件树。
2. 中间：主要代码编辑区。

- 右侧 Git 面板：约 340px。

各区域支持合理的宽度调整，但不要把窗口管理做得复杂。

三个区域之间要有清晰的视觉分隔，禁止重阴影、过多卡片、过大的圆角和花哨渐变。

默认情况下，用户打开项目后就能立即看到代码区和 Git 面板，不需要通过多个菜单进入 Git 工作区。

打开项目后，直接显示工作区。

**窗口应尽快显示，不要等待 Git 扫描、项目文件遍历或 AI 请求结束。**

## 3.2 文件树

必须支持：

- 选择本地文件夹作为项目。
- 展开和折叠目录。
- 打开文件。
- 区分文件和文件夹。
- 显示合理的文件类型图标。

- 最近打开项目。
- 刷新目录。

忽略策略需要集中配置，不要把用户源码目录意外隐藏。遵守 Git 对忽略文件的判断，不能把被忽略的依赖缓存误认为普通待提交文件。

按需加载子目录，不要在打开大型项目时递归读取所有文件内容。

首版不需要复杂的全文搜索索引服务。

# 五、Git 可视化操作

Git 是 DNACode 的核心功能之一。

右侧 Git 面板必须始终可见，不应要求用户切换到独立的 Git 工作区。

## 5.1 Git 状态

显示：

- 当前分支。
- 已暂存修改。
- 未暂存修改。
- 未跟踪文件。
- 修改文件数量。
- 暂存文件数量。
- Git 状态刷新按钮。
- 当前操作状态。

文件类型至少应识别：

- 新增。
- 修改。
- 删除。
- 重命名。
- 复制（Git 能可靠识别时）。

准确处理 Git 输出，不允许通过文件名推测文件状态。

优先使用机器可解析的 Git 输出，例如带 NUL 分隔符的 `git status --porcelain` 格式。

正确处理中文路径、空格、非 ASCII 字符及特殊文件名。

## 5.2 文件差异 Diff

选择文件后可以直接查看实际修改内容。

必须显示：

- 新增行。
- 删除行。
- 上下文代码。
- 文件路径。
- 暂存差异与未暂存差异的区别。

Diff 必须来源于真实文件内容和 Git 结果，不允许使用预置示例冒充真实修改。

对未跟踪文件，需要基于实际文件内容相对于空文件生成新增差异，不能只显示一个文件名。

正确处理二进制文件、大文件及 Git 无法预览的文件，提供合理提示，避免卡死。

可以采用单栏 Diff 视图，优先保证可读性和简洁性。

## 5.3 暂存与取消暂存

支持：

- 单个文件暂存。
- 单个文件取消暂存。
- 全部暂存。
- 取消全部暂存。

每个操作都必须真正执行 Git 命令，并在成功后刷新仓库状态。

用户未明确选择时，不要自动将全部修改放入暂存区。

不要默认丢弃文件修改。

对于丢弃修改等危险操作，必须先确认影响范围。

## 5.4 Commit

提交区域位于 Git 面板底部，包含：

- 提交信息输入框。
- AI 生成提交说明按钮。
- Commit 按钮。
- 操作中状态。
- 成功或失败反馈。

要求：

- 提交信息不能为空或只包含空白字符。
- 没有已暂存修改时，禁用 Commit。
- 不允许悄悄自动暂存未暂存文件。
- Commit 只提交已经暂存的内容。
- 提交成功后刷新状态和最近提交记录。
- 失败时保留提交信息并显示错误。
- 显示清楚的成功反馈。

这是硬性安全要求：

**Commit 必须严格遵守 Git 暂存区语义，不能为了操作方便偷偷把全部修改提交。**

## 5.5 Push

Push 必须是独立操作，由用户明确点击。

沿用用户系统已有的：

- Git 配置。
- 远程仓库。
- SSH 密钥。
- 凭据助手。
- 用户名和邮箱设置。

必须处理：

- 未安装 Git。
- 当前目录不是 Git 仓库。
- 没有远程仓库。
- 未配置提交身份。
- 远程认证失败。
- 网络失败。
- 远程拒绝推送。
- 本地分支没有上游分支。
- 其他 Git 错误。

不得自行实现 SSH 或远程 Git 协议。

不得在用户点击 Commit 后自动 Push。

Git 的原始错误信息应保留给诊断使用，同时在界面中给出易懂的说明。

## 5.6 分支与提交历史

首版支持：

- 查看当前分支。
- 查看本地分支。
- 在安全前提下切换分支。
- 查看最近提交历史。
- 显示 Commit ID、提交说明、作者和时间。
- 查看某次提交涉及的文件和 Diff。

切换分支之前检查工作区状态。

存在未提交修改时，需要阻止可能导致数据丢失的操作，或者根据实际情况要求用户确认。

历史记录采用分页或限制数量加载，不要一次性加载完整的庞大仓库历史。

不需要复杂的 Git 图形化网络图、交互式 rebase 或完整冲突编辑器。

# 六、AI 修改总结

AI 是可选功能。

**即使没有配置 AI，DNACode 的打开项目、代码编辑、Git Diff、暂存、Commit 和 Push 都必须正常工作。**

AI 只能在用户主动点击后运行。

禁止在软件启动时自动调用模型。

## 6.1 AI 配置

在设置中提供：

- API Base URL。
- API Key。
- Model Name。
- 测试连接按钮。
- 请求超时设置。
- 简单的请求限制配置。

使用适配 OpenAI 兼容 Chat Completions API 的实现，但要合理处理不同供应商的 URL 格式、响应格式及错误返回，不要假定所有供应商完全相同。

不绑定唯一模型供应商。

API Key 优先存储在操作系统的安全凭据存储中。可以使用维护良好的 Rust 凭据库。普通设置配置文件只存储非敏感信息。

如果安全凭据存储失败，明确提示用户并停止保存，不得自动把 Key 明文写进配置文件或日志。

AI 未配置时，显示如何配置的简单引导。

## 6.2 AI 总结流程

用户点击“AI 总结本次修改”后：

1. 获取真实的 Git 状态。
2. 收集所需的暂存和未暂存差异。
3. 纳入适当的未跟踪文件内容。
4. 区分新增、修改、删除等情况。
5. 排除二进制文件、过大文件和不可安全预览的内容。
6. 对大 Diff 做合理限制和分批处理。
7. 对明显的密钥、Token、密码等敏感内容进行过滤或脱敏。
8. 告知用户即将发送代码变更到其配置的模型服务。
9. 请求过程中显示加载与错误状态。
10. 将结果呈现在 Git 面板中。

用户可以选择总结全部工作区变更，或者只总结暂存内容，并明确知道两者的区别。

AI 总结应包括：

- 本次修改的整体目的。
- 主要改动。
- 关键文件变更。
- 需要注意的风险。
- 建议的 Commit Message。

总结应严格基于实际差异，不得凭空声称功能已经实现或测试已经通过。

生成的提交信息放入可编辑输入框，由用户最终确认。

AI 请求失败、超时或未配置时，不得影响其他功能。

绝不允许模型直接执行系统命令、自动修改源码或自动提交代码。

首版不开发 AI Agent、自动修复代码、自动执行命令等复杂功能。

# 七、性能要求

性能是硬性要求，不是后期可选优化。

请将以下原则融入实现：

1. 启动后尽快显示主窗口。
2. 不等待 AI、网络请求或 Git 仓库扫描结束。
3. 项目文件树按需加载。
4. 避免遍历大型依赖目录。
5. 耗时的 Git 和文件操作放到后台执行。
6. 不让 Git 操作阻塞前端交互。
7. AI 请求在后台执行，并支持合理超时和取消。
8. 避免过于频繁的 Git 状态轮询。
9. 不在每次界面更新时重新读取所有文件。
10. 只更新实际发生变化的 UI 区域。
11. 对大文件和巨大 Diff 进行限制。
12. 复用已打开文件的数据，合理缓存状态。
13. 空闲时不应产生大量 CPU 活动。
14. 不要引入不必要的常驻后台任务。
15. 避免不必要的语言包及 UI 依赖。

不要把 Rust 或 Tauri 当作自动获得高性能的保证。

在实际环境允许时测量：

- 冷启动时间。
- 空闲内存。
- 打开小型项目的体验。
- 打开中等规模项目的体验。
- Git 刷新速度。
- 切换文件和滚动代码时的响应。

测试记录应标注操作系统、硬件环境及测试项目规模。

不要编造性能数据或未经验证的结论。

# 八、Rust 后端安全

Rust 后端负责：

- 项目文件操作。
- Git 命令执行。
- Git 状态和 Diff 解析。
- 分支与提交历史。
- AI API 请求。
- 配置和凭据存储。
- 后台耗时任务。
- 错误处理和日志。

前端只能通过定义清晰的 Tauri Commands 调用后端。

必须遵守：

- 使用安全的进程调用方法执行 Git。
- 使用 `std::process::Command` 或合适的等效方式。
- 不允许把用户输入拼接进 shell 命令。
- 不允许前端传入任意命令字符串并执行。
- 对文件路径进行校验。
- 避免路径穿越和未经授权的文件访问。
- 对删除或覆盖文件的操作提供保护。
- 限制 Tauri capabilities 到最小权限范围。
- 不暴露不必要的 IPC 和系统能力。
- 不在日志中输出 Key、密码、Token 或敏感请求头。
- 后台命令失败时返回清晰错误，不让应用崩溃。
- 不因外部命令失败就终止整个主程序。

AI 上传内容必须遵守用户主动触发原则，默认不上传仓库内容，不增加任何遥测或行为数据收集。

# 十、主题与细节

默认深色主题，可以切换浅色主题。

界面尽量简洁：

- 中性色为主。
- 蓝色作为主要操作色。
- 绿色表示新增和成功。
- 红色表示删除和危险操作。
- 控制阴影与圆角。
- 合理的文字密度。
- 主要按钮应有清楚的文字。
- 图标必须意义明确。
- 重要操作需要状态反馈。

必须合理处理以下状态：

- 没有打开项目。
- 空文件夹。
- 非 Git 仓库。
- 没有任何变更。
- 没有暂存内容。
- Git 命令执行中。
- Git 命令失败。
- 没有远程仓库。
- 未配置 Git 身份信息。
- AI 未配置。
- AI 请求失败。
- 文件无法保存。
- 文件外部发生变化。

1. 桌面窗口与主界面。
2. 项目打开和文件树。

6. 提交历史与必要分支操作。
7. AI 总结与提交信息生成。
8. 设置与错误处理。
9. 性能优化。
10. 文档、测试、生产打包和发布配置。

核心 Git 流程必须使用真实 Git 仓库验证，不能用假数据代替。

执行完整测试、类型检查、lint、Rust 检查和生产构建。

读取真实错误日志，修复由本次改动导致的问题。

- README、LICENSE 和工作流所在位置。
- 尚未完成的内容及原因。
- 下一步需要用户完成的操作（如果确实存在）。

不允许把没有实现的功能写成已经完成。

不允许把没有执行的测试报告为通过。

不允许把本地构建报告为已经发布到 GitHub。
